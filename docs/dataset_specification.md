# Dataset Specification: RecoverAI

## Overview

This document specifies the dataset schema, model prediction target, data leakage prevention rules, evaluation design, business metrics, and synthetic data requirements for RecoverAI's primary workflow: **Failed Payment Recovery**.

---

## Prediction Problem Definition

The core prediction problem for RecoverAI is formulated as estimating the action-conditional probability of successful payment recovery:

$$\text{Target Function: } P(\text{recovered} = 1 \mid \text{payment context}, \text{proposed recovery action})$$

The model estimates the probability of recovery conditional on choosing one of four valid recovery actions:
- **`RETRY`**: Automated payment retry (e.g., smart timing, gateway rerouting).
- **`NUDGE`**: Customer notification (email, SMS, or app prompt to update payment method or retry).
- **`ESCALATE`**: Route to a human support agent or operator queue for manual outreach.
- **`STOP`**: Take no action and halt automated processing for this transaction.

## Field Roles & Constraints

### 1. Model Input Features vs. Historical Action
- `historical_action` represents the action actually observed in historical or simulated data.
- It is used when learning from historical action-outcome pairs to estimate $P(\text{recovered} \mid \text{context}, \text{action})$.
- During inference, candidate actions (`RETRY`, `NUDGE`, `ESCALATE`, `STOP`) are evaluated separately by passing each candidate action into the model to score recovery probabilities.
- Future outcomes (such as `recovered`, `recovered_amount_inr`, and `recovery_time_hours`) must never be used as input features.

### 2. Identifiers
- `payment_id` and `customer_id` are unique record keys used for tracking, auditing, and grouping. They **must not** be treated as numerical or predictive features during model training or inference.

### 3. Model Output
- `recovery_probability` is a **MODEL OUTPUT** field populated by the inference model. It must never be used as an input feature for model training.

### 4. Outcome & Evaluation Only Fields (Data Leakage Target Controls)
The following fields represent post-intervention outcomes and must **NOT** be used as model input features during training or decision inference:
- `recovered` (Model Target / Ground Truth)
- `recovered_amount_inr` (Evaluation Metric)
- `recovery_time_hours` (Evaluation Metric)

---

## Data Leakage Prevention

Data leakage occurs when information generated after an action is taken is inadvertently fed into the decision model prior to action execution.

To guarantee zero data leakage:
1. **Temporal Boundary Enforcement**: Only features available at or before the decision timestamp $t_0$ are included as model inputs.
2. **Outcome Isolation**: Post-action ground truth fields (`recovered`, `recovered_amount_inr`, `recovery_time_hours`) are strictly segregated into evaluation containers and cannot enter feature engineering pipelines.
3. **Feature Preprocessing Boundaries**: Scalers, encoders, and imputer transformers must be fitted **exclusively** on training splits, then applied to validation and test splits without refitting.

---

## Train / Test Evaluation Design

To validate RecoverAI's performance rigorously:

1. **Held-Out Test Set**: A final chronological test set must be strictly held out from all model selection, hyperparameter tuning, and training phases.
2. **Preprocessing Isolation**: All feature engineering transformations (scaling, encoding, target encoding) must be fit solely on the training partition.
3. **Dual-Axis Evaluation**:
   - **Predictive Performance**: Evaluated using ROC-AUC, PR-AUC, Brier score (calibration), and log-loss.
   - **Monetary Recovery Performance**: Evaluated by quantifying net financial recovery across the test batch.
4. **Baseline Comparison**: RecoverAI's decision strategy must be benchmarked against baseline strategies:
   - *Naive Retry-All*: Automatically retries every failed payment up to max attempts.
   - *Static Rule-Based*: Fixed rules (e.g., retry soft declines, nudge hard declines).
   - *No Intervention*: Baseline where no recovery actions are taken.

---

## Counterfactual Evaluation Design

Because RecoverAI must choose among multiple possible recovery actions, the synthetic data generation process will maintain hidden potential outcomes for each payment-action pair:

- $P(\text{recovered} \mid \text{context}, \text{RETRY})$
- $P(\text{recovered} \mid \text{context}, \text{NUDGE})$
- $P(\text{recovered} \mid \text{context}, \text{ESCALATE})$
- $P(\text{recovered} \mid \text{context}, \text{STOP})$

Only the outcome corresponding to the action actually selected (`historical_action`) will be exposed as the observed historical outcome in the main dataset.

The hidden potential outcomes will be retained separately for controlled policy evaluation and will never be provided as model features.

This allows RecoverAI's learned policy to be compared fairly against baseline policies in the synthetic test environment without leaking future outcomes into the decision model.

## Business Metrics

The system will be evaluated using the following key business and financial metrics:

$$\begin{aligned}
\text{Revenue at Risk} &= \sum \text{amount\_inr for all failed payments} \\
\text{Revenue Recovered} &= \sum \text{recovered\_amount\_inr for all recovered payments} \\
\text{Recovery Rate} &= \frac{\text{Count of recovered payments}}{\text{Count of total failed payments}} \\
\text{Expected Recovered Amount} &= \sum \left( \text{amount\_inr}_i \times \text{recovery\_probability}_i \right) \\
\text{Unnecessary Retry Rate} &= \frac{\text{Count of failed RETRY actions on non-recoverable payments}}{\text{Total RETRY actions}} \\
\text{Escalation Rate} &= \frac{\text{Count of ESCALATE actions}}{\text{Total failed payments}} \\
\text{Guardrail Block Rate} &= \frac{\text{Count of decisions overridden by guardrails}}{\text{Total evaluated decisions}} \\
\text{Recovery Cost} &= \sum \text{action\_cost\_inr for all executed actions} \\
\text{Net Recovered Revenue} &= \text{Revenue Recovered} - \text{Recovery Cost}
\end{aligned}$$

## Synthetic Data Requirements

When creating the synthetic dataset in future steps, the data generator must strictly fulfill the following realism constraints:

1. **Causal & Domain Correlation**: Columns must reflect realistic domain dependencies (e.g., hard declines like `stolen_card` have near-zero recovery rates for `RETRY`; soft declines like `network_timeout` have high recovery rates for `RETRY`).
2. **Action-Dependent Outcomes**: The outcome `recovered` must depend joint-wise on both failure context and the chosen `historical_action` (e.g., a `NUDGE` for expired cards has higher recovery than a `RETRY`).
3. **Non-Independent Distributions**: Do not generate independent random columns. Customer history (e.g., `previous_successes`, `customer_tenure_days`) must correlate realistically with `historical_payment_success_rate` and `customer_lifetime_value_inr`.
